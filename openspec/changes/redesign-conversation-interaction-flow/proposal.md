## Why

当前旅行对话页已经具备持久化消息、规划需求单和独立 Run 生命周期，但前端将消息、需求单与任务卡分区渲染，导致用户难以理解“为什么出现这张卡、当前需要做什么、结果在哪里”。同时“新建规划”和“旅行对话”形成两套入口与两套进度表达，需要统一为一条连贯、可恢复且可访问的对话式规划体验。

## What Changes

- **BREAKING**：将“旅行对话”确立为创建、继续和恢复旅行规划的唯一默认入口；移除“首页”和“新建规划”导航。“首页”的默认落点、品牌点击与退出登录后均进入旅行对话。
- 登录或注册完成后恢复用户原先想进入的页面或动作，避免认证后返回首页丢失上下文。
- 将消息、规划需求摘要、任务状态与结果预览按发生顺序组织为统一时间线，并在原位置持续更新对应实体。
- 用渐进式、结构化提问收集必填与可选旅行需求；显示已理解内容、缺失项和默认值，并在正式运行前要求明确确认。
- 将内部 Agent 节点压缩成少量用户可理解的规划阶段，不展示虚假百分比或内部推理。
- 为 `queued`、`running`、`waiting_user`、`succeeded`、`failed` 和 `cancelled` 提供清晰、可恢复且动作明确的展示。
- 在规划后台运行时保持对话输入可用，并为离开视口的活动任务提供轻量状态提示。
- 当用户试图修改正在执行的不可变请求时，明确提供“按新要求重新规划”或“完成后创建修改任务”的选择。
- 完成态先展示可理解的成果摘要，再提供打开行程、继续修改等后续操作。
- 补充键盘操作、焦点管理、状态播报、非颜色状态标识和移动端重排要求。

## Capabilities

### New Capabilities

- `conversation-entry-flow`: 统一规划入口、认证后恢复目标动作以及空状态的任务引导。
- `conversation-activity-timeline`: 在持久化对话中按因果和时间顺序混排消息、需求、任务与结果。
- `guided-planning-brief`: 通过渐进式问题、结构化控件和可编辑摘要收集并确认正式规划需求。
- `planning-task-presentation`: 面向用户呈现规划任务的排队、阶段进度、等待输入、终态、恢复和多任务状态。

### Modified Capabilities

无。当前仓库尚无主规格；本变更以新增能力定义现有运行时之上的前端产品契约。

## Impact

- 主要影响 `frontend/main.jsx`、`frontend/pages.jsx`、`frontend/components.jsx`、`frontend/chat-state.js` 和 `frontend/style.css`。
- 可能扩展前端实体排序、活动任务摘要和输入控件映射；优先复用现有 conversations、messages、planning briefs、runs、events、resume、cancel 与 retry API。
- 需要调整导航与认证成功回调，但不改变 Run 生命周期、不可变请求快照、SSE 安全过滤或行程结果的数据权威边界。
- 现有 `PlanPage` 的独立入口将被降级为仅供行程修改使用的兼容路径；行程详情、历史行程、画像和编辑能力继续保留。
- 需要增加 reducer、组件交互、路由恢复、响应式布局及无障碍状态的前端测试。
